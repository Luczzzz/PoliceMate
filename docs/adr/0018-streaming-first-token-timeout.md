# ADR-0018：流式首字等待改用独立超时，与段间空闲分开

- 状态：已接受
- 关联：取代 ADR-0015 第 7 条中「空闲超时……含首字等待」的口径。部署证据见
  `docs/agents/deploy-agent-log.md`（7.2、8.1、8.2、9.3）。

## 背景

ADR-0015 第 7 条用一条空闲超时同时约束「等首字」和「等下一段」，默认 30 秒。上线后实测这两件事的
时间尺度不同量级：

| 口径 | 实测 | 目标 |
| --- | --- | --- |
| 首字延迟（本机） | 11.3–22.7 秒 | ≤10 秒 |
| 首字延迟（公网） | 10.7 / 17.0 / 28.8 / 31.1 / 40.6 秒 | ≤10 秒 |
| 段间跨度（公网） | 9–19 秒 | — |

按默认 30 秒，本机 5 例里有 1 例、公网口径下 5 例里有 2 例会**在首字阶段**被判 `idle_timeout`：
用户看到 0 字和「内容不完整」，而这不是上游出错，只是首字慢。

部署侧已用 `PM_STREAM_IDLE_TIMEOUT_MS=45000` 临时兜住，并明确判断这只是掩盖症状，建议二选一：
① 把首字等待与中途空闲拆成两个超时；② 提高 `PM_STREAM_IDLE_TIMEOUT_MS` 默认值。本 ADR 选①。

## 决策

1. **首字等待用独立预算**：新增 `PM_STREAM_FIRST_TOKEN_TIMEOUT_MS`，默认 60 秒（实测上限 40.6 秒
   之上留余量）。超时以新的中断原因 `first_token_timeout` 结束。
2. **空闲超时只管首字之后的间隔**，默认回到 30 秒。实测段间跨度 9–19 秒，30 秒足够；两者混在
   一起才会被迫把段间空闲也抬到 45 秒。
3. **实现要点：循环前不得 `armIdle()`。** `armIdle()` 的语义是「收到一段之后，为下一次等待重新
   计时」，所以首字那一轮等待本来就不该有它。收到首字后清掉首字计时器并 `armIdle()`，此后每个
   间隔都由空闲超时约束。这一点必须写在代码注释里：把它写成「首段到达时跳过 `armIdle()`」的
   标志量版本会连带豁免首字到第二段之间的间隔，使中途卡死要等总时限才失败。
4. **中断原因区分开**：`StreamAnalysisInterruptReason` 增加 `first_token_timeout`。拆成两个预算的
   全部理由就是这两件事含义不同；若中断原因仍合并，遥测里「首字慢」与「中途卡死」无法区分，
   而线上失败定位本来就已因遥测不落盘而困难（deploy-agent-log 7.3）。
   前端不区分两种超时，都显示「生成中断，内容不完整」，因此前端无需改动。
5. **不改变**：`PM_REPORT_TIMEOUT_MS` 总时限语义不变；首字预算必须小于总时限才有意义。

## 已知风险

- **没有降低首字延迟本身。** ADR-0015 验收项「首字延迟中位 ≤10 秒」仍未达标（公网中位 28.8 秒），
  本 ADR 只保证慢首字不再被误杀。真正的提速在上游/提示词侧，属于另一项工作。
- **上游完全挂死时，探测变慢**：首字阶段从 30 秒才发现变成 60 秒才发现。这是刻意取舍：首字慢是
  实测常态，而前端全程显示「正在生成…」并提供「停止」按钮，用户可以主动结束。
- 部署侧必须显式调整环境变量，否则线上仍按 `PM_STREAM_IDLE_TIMEOUT_MS=45000` 跑，且不知道新变量
  存在（已在 `docs/agents/deploy-agent-log.md` 的开发端回复中说明）。

## 验收

- 单元：首字耗时超过 `PM_STREAM_IDLE_TIMEOUT_MS` 但小于首字预算时仍 `complete`；首字长期不来以
  `first_token_timeout` 结束；首字之后的间隔仍以 `idle_timeout` 结束；总时限仍以 `total_timeout`
  结束。
- 部署：把 `PM_STREAM_IDLE_TIMEOUT_MS` 从 45000 改回 30000，并设置 `PM_STREAM_FIRST_TOKEN_TIMEOUT_MS`
  后，用虚构案情重跑 ADR-0015 的 5 例流式验收，确认 5/5 `complete` 且首字延迟数字照实记录。
