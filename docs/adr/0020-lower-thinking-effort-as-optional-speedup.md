# ADR-0020：降低思考强度作为可选的提速手段，默认关闭

- 状态：已接受
- 关联：ADR-0019（调用预算与首字归因）、ADR-0014（直连 LLM 提供者）、ADR-0016（事故责任认定辅助）。
  部分回应 ADR-0019 已知风险里"提速幅度未经验证"这一项。

## 背景

ADR-0019 之后仍有一件事没有答案：首字延迟（公网实测 6.7–41.2 秒）里，有多少是模型在
`reasoning_content` 里思考，而不是载荷或排队。若主要是思考，那么最直接的提速手段就是降低
思考强度。

问题是这个开关不是"改一个数"：OpenAI 兼容层对"思考强度"没有统一字段名——`reasoning_effort`
（OpenAI 风格）、`thinking: {type: "disabled"}`（Anthropic 风格）、`enable_thinking`
（Qwen/vLLM 风格）、`chat_template_kwargs.enable_thinking` 都在被使用。而本项目的上游已经
在 `json_schema` 上被拒过一次（部署日志 6.4），说明**未知字段会让网关直接 400**。猜字段名发出去，
风险是让整个功能从"慢"变成"不可用"。

## 决策

1. **只接线两种方言，默认都不发。** 新增 `PM_LLM_REASONING_EFFORT`（直传 `reasoning_effort`）
   与 `PM_LLM_THINKING=off`（发 `thinking:{type:"disabled"}`）。两者都不设时，请求体与引入本能力
   前逐字节一致——这条有单测守着，因为"默认不改变线上请求"比"多一个开关"更重要。
2. **两者互斥，同时设置启动即报错。** 语义重叠时静默取一个会让线上行为不可解释。
3. **先用探测脚本确认网关吃哪一种，再写环境变量。** 新增 `npm run llm:thinking`：逐个变体
   （baseline / reasoning_effort=minimal / =low / thinking.disabled / enable_thinking=false /
   chat_template_kwargs）单独发请求，只打印 HTTP 状态、是否出现思维链、思维链字符数、首个思维链与
   首个正文字符的到达时间。它同时回答"这个模型到底是不是推理模型"——baseline 没有思维链，
   思考强度开关就毫无意义，首字慢的原因必须另找。
4. **降低思考强度是有代价的取舍，不是白拿的优化。** 思考长度与"条号写错、漏引"负相关，而
   产品的核心边界是"不给出没核对过的条号"。因此切换前后必须对比同一组虚构案情的
   「〔条号未经核对〕」出现次数——这是这条取舍唯一可测的质量指标（ADR-0019 的事后核对正好免费
   提供它）。
5. **`max_tokens` 与思考强度的关系写清。** 额度是"思维链 + 正文"合计：降低思考强度会让同一额度
   更宽松，反之亦然。因此两个开关不要分开调，`PM_LLM_MAX_TOKENS_*` 已在 ADR-0019 按合计口径放宽。

## 已知风险

- **最可能的现实结果是"都不支持"。** 自建或第三方网关常常把这些字段一起剥掉或直接拒绝；届时
  可选路径只剩：换非推理模型、让网关侧支持、或只做感知延迟优化（等待弹窗、流式）。
- **探测脚本本身会消耗上游配额**（6 个短请求），且如果模型思考很长，单次可能几十秒。
- **`enable_thinking` 两种写法本仓库未接线**，只用于探测：确认可用后再接线，避免同时发多种方言。
- **降低思考后延误可能只是从"等首字"变成"等返工"**：报告里被降级的条号越多，民警核对成本越高。
  这个代价不进延迟指标，但进可用性。

## 验收

- 单元：默认请求体不含任何思考字段；设置 `PM_LLM_REASONING_EFFORT` 只发该字段；设置
  `PM_LLM_THINKING=off` 只发 `thinking:{type:"disabled"}`；取值不在白名单或两者同时设置时启动失败。
- 部署：跑 `npm run llm:thinking`，把每个变体的接受/拒绝、思维链字符数与总耗时照实记入
  `docs/agents/deploy-agent-log.md`；只有被接受且确实减少思维链的变体才写进生产环境变量。
- 质量：同一组虚构案情在切换前后各跑一次，比较「〔条号未经核对〕」出现次数与责任认定结论是否变化。
